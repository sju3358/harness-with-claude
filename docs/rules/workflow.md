# 작업 흐름과 승인 게이트

이 문서가 절차의 단일 원본이다. 스킬은 이 문서의 단계를 실행하는 방법을 적는다.

## ID 체계

| ID | 형식 | 정의 위치 | 예 |
| --- | --- | --- | --- |
| 요구사항 | `REQ-###` | `docs/requirements.md` 표 | `REQ-001` |
| feature | `F-##` | `docs/prd/00-overview.md` feature 목록 | `F-01` |
| API | `API-###` | `docs/api/README.md` 엔드포인트 제목 (feature 명세 API 표가 feature·REQ 연결) | `API-007` |
| 테스트 케이스 | `TC-F##-##` | `artifacts/work/F-##/PLAN.md` | `TC-F01-03` |

- ID는 한번 정하면 바꾸거나 재사용하지 않는다. 삭제된 요구사항은 행을 지우지 않고 상태를 `삭제`로 바꾼다.
- 티켓마다 브랜치가 따로라서, 새 ID(`REQ`·`Q`·`F`·`API`)는 `git fetch` 후 통합 브랜치(`origin/main`)와 아직 병합되지 않은 다른 작업 브랜치(`git branch -a --no-merged origin/main`)의 문서에서 쓰인 최댓값 다음 번호로 정한다.
- PRD의 모든 규정 문장은 근거 REQ를 함께 적는다. REQ 없이 PRD에 들어간 내용은 "출처 없음"으로 검증에서 걸린다.
- 테스트는 `@DisplayName` 또는 주석에 `TC-F##-##`와 `REQ-###`를 적어 추적한다.
- 누락 검사는 `sh scripts/check-trace.sh prd`, `sh scripts/check-trace.sh feature F-##`로 기계적으로 한다.
- API 문서와 코드의 엔드포인트 목록 비교는 `node scripts/check-api.mjs [F-##]`로 한다.

## 작업 단위와 브랜치

- 티켓 하나 = feature 하나 = 브랜치(`feat|fix/ITD-####`) 하나. 그 feature의 요구사항·PRD·API 문서·개발계획·구현·테스트·검증을 같은 브랜치에서 진행한다.
- 모든 단계를 Claude가 한 흐름으로 이어서 한다. 단계마다 담당을 나누지 않고, 앞 단계가 끝나면 같은 세션에서 다음 단계로 넘어간다. 멈추는 곳은 승인 게이트, 사람 승인 필요 항목, PRD 변경(사용자 결정), 환경 문제뿐이다.
- worktree를 만들지 않는다. 프로젝트 폴더 하나에서 `work-start`가 통합 브랜치(`main`)로부터 작업 브랜치를 만들어 전환(`git switch -c`)하고, 그 세션에서 바로 이어 간다.
- 통합 브랜치에서는 `project-init`, `work-start`, 하네스 도입·업데이트만 하고 문서·계획·코드를 편집하지 않는다(`edit-guard` 훅이 차단).
- 한 번에 티켓 하나만 진행한다. 다른 티켓으로 전환하려면 지금 브랜치의 변경을 커밋한 뒤 `work-start`를 다시 한다.
- 하네스는 최신으로 유지한다. 세션 시작 때 `SessionStart` 훅이, 티켓 시작 때 `work-start`가 `.harness/hooks/harness-version.sh`로 설치 버전(`.harness/version`)과 원본 `main` 커밋을 해시로만 비교한다(최신이면 출력 없음). 다르면 `harness-update` "0. 업데이트 시점 판단"대로 바뀌는 내용과 진행 중 티켓 영향을 확인한 뒤 업데이트한다. 기본 시점은 새 티켓 시작 전(통합 브랜치)이고, 진행 중인 티켓은 사용자가 원할 때만 중간에 반영한다.
- `docs/requirements.md`에는 이 티켓 범위의 REQ만 적는다(`check-trace.sh prd`는 모든 REQ가 PRD에 반영됐는지 본다). 다른 feature의 요구는 별도 티켓 후보로 보고한다.

## 단계

| 단계 | 스킬 | 산출물 | 완료 기준 |
| --- | --- | --- | --- |
| C0 초기 셋팅 | `project-init` | `docs/project.md`, Git 훅 등록 | 통합 브랜치에서 프로젝트당 1회. 스택·DB·MQ·검증 명령을 사용자에게 확인받음 |
| W 작업 시작 | `work-start` | `feat/ITD-####` 브랜치로 전환 | 통합 브랜치에서 실행. 하네스 버전 확인(구버전이면 `harness-update` 먼저). 티켓 번호 사용자 확인 |
| C1 요구사항 | `req-gather` | `docs/requirements.md` | 이 티켓의 요구사항마다 REQ ID·출처·인수 기준, 미결 질문 분리 |
| C2 PRD | `prd-write` | `docs/prd/**` | 이 티켓의 모든 REQ가 PRD 어딘가에 반영, feature 명세 확정 |
| C2b API 문서 | `api-design` | `docs/api/README.md` (FE 전달용 한 장) | PRD의 모든 API가 필드·에러까지 문서화. 다른 문서 참조 없이 자체 완결, FE에 필요 없는 내부 정보 없음 |
| C3 PRD 검증 | `prd-verify` | `docs/verification/prd-verify.md` | `prd-verifier`(새 컨텍스트) 판정표(요구사항 ↔ PRD ↔ API), `check-trace.sh prd` 통과. 마지막 전체 회차 `승인 가능`(차단 0건) 후 문서 변경 없음 |
| ✋ PRD 승인 | `prd-verify` | `requirements.md`·`00-overview.md`·`docs/api/README.md` 상태 `승인 vX.Y` | 사용자가 `PRD 승인` 입력. API 문서도 함께 승인됨 |
| C4 개발계획 | `feature-plan` | `artifacts/work/F-##/PLAN.md`, `HANDOFF.md` | REQ ↔ 변경 파일 ↔ TC 매핑, 확인 필요 항목 답변 완료 |
| ✋ 계획 승인 | `feature-plan` | 승인 기록 | 사용자가 `계획 승인` 입력 |
| C5 구현 | `implement` | 소스·빌드 파일 | 컴파일 통과. 파일 묶음마다 `HANDOFF.md` "진행 위치" 갱신. 계획 이탈은 `PLAN.md` "계획 변경 이력"과 재승인 |
| C6 문서-코드 검증 | `doc-code-verify` | `VERIFY.md` | `code-verifier`(mode=code) 판정표, REQ마다 `파일:줄` 근거. 마지막 전체 회차 `수정 필요` 없음, 그 뒤 소스 변경 없음 |
| C7 API 검증 | `api-verify` | `API-VERIFY.md` | `check-api.mjs` 통과, `code-verifier`(mode=api) 엔드포인트·항목별 판정. 마지막 전체 회차 불일치 없음, 그 뒤 소스 변경 없음 |
| C8 테스트 작성 | `test-write` | 테스트 코드, `test-status.md` | `PLAN.md`의 TC 전부 구현(명세 누락 TC는 보류 사유와 함께) |
| C9 테스트 검증 | `test-verify` | `TEST-REPORT.md`, `test-status.md`, `docs/traceability.md` | 모든 TC `PASS`(실행 결과 원문), `check-trace.sh feature` 통과, `code-verifier`(mode=test)의 유효성 판정. 완료는 전체 회귀 실패 0건(이후 소스·테스트 변경 없음)일 때만 |
| ✋ 커밋·푸시 승인 | `itd-commit` | 커밋, 작업 브랜치 push | 테스트·검증 미완료면 경고 1회 후 사용자 판단. 사용자가 `커밋 승인`·`푸시 승인` 입력 |

- 구현과 테스트를 같은 흐름에서 쓰므로 작성자와 판정자를 컨텍스트로 나눈다. 판정(PRD·문서-코드·API·테스트 유효성)은 항상 새 컨텍스트의 검증 에이전트(`prd-verifier`, `code-verifier`)가 원문만 보고 한다. 메인 세션은 자기 결과를 "검증 완료"로 보고하지 않는다.
- 테스트 기대값은 문서(요구사항·PRD·API·`PLAN.md`)에서만 가져온다. 구현 코드는 인터페이스·실행 방법 확인용이고, 문서와 다르면 버그, 문서가 침묵하면 명세 누락으로 기록한다. 구현할 때 기억한 동작도 기대값의 근거가 아니다. `code-verifier`(mode=test)는 문서 근거 없이 구현과만 일치하는 단언을 `무효(구현 추종)`로 판정한다.
- 테스트는 첫 실패에서 멈춘다. 원인을 분류하고, 구현 결함이면 `HANDOFF.md` "구현 수정 요청"에 버그 리포트를 먼저 쓴 뒤 `implement`로 구현을 고치고 다시 돌린다. 구현을 고칠 때 테스트 기대값은 바꾸지 않는다.
- 중간 재실행은 `test-status.md` 기준으로 `FAIL`·`미실행`과 수정 파일에 관련된 `PASS` TC만 한다. 최종 완료 판정은 전체 회귀(전체 테스트) 통과가 필수다. 모든 TC가 `PASS`가 되면 전체 회귀를 실행하고, 실패 0건이며 그 뒤 소스·테스트 변경이 없을 때만 `HANDOFF.md` 상태를 `완료`로 쓴다. 충족하지 않은 채 커밋하면 `itd-commit`이 경고하고 `- 미검증: 전체 회귀`를 남긴다.
- 테스트·검증이 끝나지 않아도 커밋·push를 막지 않는다. `itd-commit`이 미충족 항목을 근거와 함께 1회 경고하고, 사용자가 진행 여부를 정한다. 진행하면 커밋 본문에 `- 미검증: <항목>`을 남긴다.
- 커밋에 들어갈 인계 기록(`HANDOFF.md` 상태·다음 행동)은 커밋 전에 갱신해 같은 커밋에 넣는다. 커밋·push 뒤에는 파일을 고치지 않는다(작업 트리가 다시 바뀌면 `main` 전환 전에 커밋·승인을 또 받아야 함).

### 세션 인계 (토큰 한도·계정 전환)

Claude 계정 두 개를 번갈아 쓴다. 한 계정의 토큰이 떨어지면 다른 계정이 같은 폴더에서 새 세션을 열어 이어 간다. 대화 맥락은 넘어가지 않으므로 **맥락은 파일로 이어 간다.**

- 두 계정을 동시에 쓰지 않는다. 앞 계정 세션이 멈춘 뒤 다음 계정 세션을 연다. 같은 폴더를 두 세션이 동시에 편집하면 변경이 섞인다.
- 인계 기준은 작업 브랜치의 파일이다: `HANDOFF.md` "상태"·"진행 위치", `PLAN.md`, 검증 산출물, `test-status.md`, `git status`·`git diff`. 자동 기억(memory)이나 이전 세션 재개(`--resume`)에 기대지 않는다(계정 전환 방식에 따라 계정마다 따로 저장돼 보이지 않을 수 있음).
- `HANDOFF.md` "진행 위치"는 언제 끊겨도 되게 자주 갱신한다: 구현·테스트 작성 중 파일 묶음마다, 단계를 시작·마칠 때, 검증 에이전트를 실행하기 직전(`<스킬> 회차 N 실행 중`). `HANDOFF.md`가 생기기 전(C1~C3)에는 문서 자체(`- 버전:`·`- 상태:` 줄, `prd-verify.md` 회차)가 진행 위치다.
- 새 세션이 작업 브랜치에서 시작·재개·압축되면 `SessionStart` 훅(`.harness/hooks/session-context.sh`)이 `HANDOFF.md`의 상태·진행 위치(없으면 문서 단계의 버전·상태와 마지막 PRD 검증 회차), 승인 상태, `git status`를 컨텍스트로 넣는다. 새 세션은 이 내용과 `git diff`로 실제 진행을 확인하고, 다르면 실제 변경을 기준으로 진행 위치를 먼저 바로잡은 뒤 이어 간다.
- 결론 줄(`### 결론:`)이 없는 검증 회차는 세션이 끊긴 회차다. 판정 근거로 쓰지 않고 제목 끝에 `(중단)`을 붙인 뒤 다음 번호로 다시 실행한다.
- 승인 기록(`.harness/state/`)은 폴더에 남으므로 계정이 바뀌어도 유효하다. 커밋·푸시 승인은 30분이 지나면 다시 받는다.

PR 생성과 병합은 사람이 직접 한다. 에이전트는 PR을 만들지 않는다. 병합 후 정리(`git switch main`, `git pull`, `git branch -d`)는 사용자가 한다.

## 승인 게이트

| 게이트 | 입력 문구 | 기록 | 막는 동작 |
| --- | --- | --- | --- |
| PRD 승인 | `PRD 승인` | `.harness/state/prd-approved` (요구사항·PRD·API 문서 해시) | `feature-plan` 진행 |
| 계획 승인 | `계획 승인` | `.harness/state/plan-approved--<브랜치>` | 소스·빌드 파일·테스트 코드 편집 |
| 커밋 승인 | `커밋 승인` | `.harness/state/git-approved`(30분) | `git commit` |
| 푸시 승인 | `푸시 승인` | `.harness/state/git-approved`(30분) | `git push` |
| 하네스 도입 (예외) | `하네스 도입 승인` | `.harness/state/adopt-approved`(30분, 승인 브랜치 한정, push 1회 후 삭제) | 보호 브랜치 커밋·push. 하네스 파일만 허용 |
| 취소 | `승인 취소` | 현재 브랜치 계획 승인·git 승인·도입 승인 삭제 | - |
| 하네스 끄기·켜기 | `하네스 OFF` / `하네스 ON` | `.harness/state/harness-off` (`하네스 ON`까지 유지) | OFF 중에는 위 게이트와 훅 차단 전부 해제 |

- 기록은 `.harness/hooks/record-approval.sh`(UserPromptSubmit)가 사용자 문장에서만 만든다. 에이전트는 `.harness/state/`를 읽기를 포함해 직접 다루지 않는다(`approval-gate` 훅이 차단).
- 승인 상태는 `sh .harness/hooks/approval-status.sh`로 확인한다. 작업 브랜치 세션이 시작·재개·압축될 때는 `SessionStart` 훅이 이 요약을 자동으로 넣는다.
- 기록은 프로젝트 폴더의 `.harness/state/`에 남아 어느 계정의 세션이든 함께 본다. 승인 문구는 해당 티켓 브랜치로 전환된 상태에서 입력한다. 계획 승인은 브랜치별로 남고, PRD 승인은 문서 해시라 다른 티켓 브랜치로 전환하거나 통합 브랜치를 반영해 문서가 바뀌면 다시 승인한다.
- 에이전트는 승인이 필요한 시점에 멈추고, 무엇을 승인하는지 요약한 뒤 입력할 문구를 안내한다. "진행해", "ㄱㄱ" 같은 일반 응답은 승인 문구가 아니므로 문구를 다시 안내한다.
- 계획 승인 후 계획이 바뀌어야 하면(파일 추가, 범위 변경, 신규 라이브러리, 판정 불가 TC, 테스트 의존성 추가) 구현·테스트 작성을 멈추고 사용자가 `승인 취소`를 입력한 뒤 `PLAN.md`를 고쳐 `계획 승인`을 다시 받는다.

## 예외: 진행 중 프로젝트에 하네스 도입

하네스가 없는 프로젝트에 중간 도입할 때만 `harness-adopt` 스킬로 위 절차를 건너뛴다.

- 건너뛰는 것: PRD 승인, 작업 브랜치, ITD 커밋 형식, 보호 브랜치 커밋·push 차단
- 지키는 것: 사용자 승인(`하네스 도입 승인`), 하네스 파일(`.harness/paths`)만 커밋, git 안전 규칙
- 훅이 강제: 보호 브랜치 커밋 시 staged 파일이 모두 `.harness/paths` 안에 있어야 하고, `git add`와 `git commit`을 한 명령에 묶을 수 없다. push할 커밋에 하네스 밖 파일이 있으면 막는다.
- 도입 커밋 이후의 모든 작업(요구사항, PRD, 기존 규약 추출, 기능 구현)은 일반 절차를 따른다.
- 하네스 업데이트(`harness-update`)도 같은 예외를 쓴다. 승인 문구는 `하네스 업데이트 승인`이고 범위는 같다(하네스 파일만).

## 되돌림

되돌림은 모두 같은 작업 브랜치 안에서 `HANDOFF.md`로 기록하며 진행한다.

- PRD 문제 발견(구현·검증·테스트 중) → `HANDOFF.md` "PRD 변경 요청" → `prd-change`(사용자 결정) → 재검증, `PRD 승인` → `feature-plan`으로 `PLAN.md` 맞춤, `계획 승인` → 중단했던 단계 재개.
- 검증·테스트에서 소스 결함 발견 → `HANDOFF.md` "구현 수정 요청"에 기록 → `implement` 3단계로 반영 → 요청이 나온 단계에서 같은 REQ에 걸린 항목을 다시 검증. 테스트는 실패했던 TC, 미실행 TC, 수정 파일과 관련된 PASS TC를 다시 실행한다(`test-verify` "재실행 범위").
- 테스트 작성 중 TC를 그대로 구현할 수 없음 → `feature-plan`(재계획) → `승인 취소` 후 `계획 승인` → `test-write` 재개.
- API 문서와 코드가 다르면 코드를 문서에 맞추는 것이 기본이다. 문서를 바꿔야 하면 "PRD 변경 요청"으로 처리하고 `prd-change`에서 `api-design` 3단계(변경 이력·프론트 영향)를 거친다.

## 검증 원칙

- 작성자와 검증자를 분리한다. 검증은 새 컨텍스트의 에이전트가 원문(요구사항·PRD·코드·테스트 결과)을 직접 읽고 판정한다. 에이전트 프롬프트에 작성 의도·자기평가를 넣지 않는다.
- 수정 후 재검증은 영향 범위만 한다(`범위: 영향`). 직전 회차의 지적 항목과, 바뀐 문서·소스에 걸린 REQ(API 검증은 엔드포인트)가 대상이다. 그 REQ가 인용된 문서·코드는 모두 다시 본다.
- 다음 단계로 넘어가기 전에 전체 검증(`범위: 전체`) 1회가 필수다. 마지막 전체 회차가 통과하고 그 뒤 대상(문서·소스)이 바뀌지 않아야 한다. 첫 회차가 전체이고 바로 통과했으면 그 회차로 충족한다. PRD 검증은 `PRD 승인` 훅이 회차의 문서 해시로 강제하고, 문서-코드·API 검증은 각 스킬의 다음 단계 조건과 `itd-commit` 확인으로 지킨다. 테스트는 `test-verify`의 선별 재실행·전체 회귀가 같은 구조다.
- PRD 검증 지적은 `차단`(누락·모순·변형·근거 없음 등 해석이 갈리는 것)과 `권고`(의미가 바뀌지 않는 문구·표기)로 나눈다. `권고`만 남으면 통과다. 최종 전체 회차의 권고는 고치면 문서가 바뀌어 전체 검증을 다시 해야 하므로 목록으로 보고한다.
- 검증 에이전트의 결과를 그대로 사용자에게 넘기지 않는다. 메인 세션이 위험이 큰 항목(사람이 바로 승인할 항목, 구체적이지만 주관적인 "일치" 주장, "변경 없음" 단정)을 골라 직접 재현해 본 뒤 보고한다. 재현 결과가 다르면 나머지 "통과" 항목도 다시 확인한다.
- "확인 못한 부분"은 "통과"와 같은 비중으로 생략 없이 보고한다.
- 테스트 통과 주장에는 실제 실행 명령과 결과 요약(성공·실패 수)을 붙인다. 실행하지 않은 테스트를 통과로 쓰지 않는다.
