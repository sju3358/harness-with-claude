# 테스트 작성

구현과 테스트를 같은 흐름에서 쓰므로, 테스트가 구현을 따라가지 않게 하는 것이 이 스킬의 핵심이다. 기대값은 문서에서만 가져오고, 유효성은 `test-verify`에서 `code-verifier`(mode=test)가 따로 판정한다.

## 1. 전제

- `VERIFY.md`·`API-VERIFY.md`의 `수정 필요`가 모두 해소됐는지 확인한다. 남아 있으면 `implement` 3단계로 먼저 반영한다.
- `PLAN.md` 상태가 `승인됨`이어야 한다(테스트 편집도 계획 승인 기록이 있어야 훅이 허용).
- `docs/project.md`의 테스트 스택(JUnit 5, AssertJ, Mockito, Testcontainers 여부)을 따른다.

## 2. 기준

- 테스트의 기대 결과는 기획·개발 문서에서만 가져온다: `docs/requirements.md`의 인수 기준, `docs/prd/features/F-##.md`·`02-common.md`의 규정, `docs/api/`의 필드·에러, `PLAN.md` TC의 시나리오와 기대 결과.
- 구현 코드는 테스트 대상의 구조, 인터페이스(클래스·메서드·엔드포인트 시그니처), 실행 방법을 파악하는 용도로만 읽는다. 코드의 "현재 동작"을 기대값으로 삼지 않는다. 구현할 때 기억한 동작도 근거가 아니다.
- 각 단언의 기대값 옆에 근거 문서 위치를 주석으로 단다(예: `// F-02#인수 조건 1`). 근거를 적을 수 없는 값은 쓰지 않는다.
- 문서와 구현이 다르면 기대값을 구현에 맞추지 않는다. 문서대로 단언하고, 그 테스트가 실패하면 구현 결함(버그)으로 다룬다(`test-verify` "실패 처리").
- 문서에 없는 동작(PRD·PLAN이 침묵)은 추측으로 기대값을 정하지 않는다. 그 동작은 테스트하지 않고 `TEST-REPORT.md` "명세 누락"과 `HANDOFF.md` "PRD 변경 요청"에 적는다. TC 전체가 판정 불가면 그 TC만 작성하지 않고 `test-status.md`에 `미실행`(사유: 명세 누락)으로 둔 채 나머지 TC는 계속 작성한다. 그 TC가 `PASS`가 되기 전에는 완료 판정이 나지 않는다(`test-verify` 6단계).

## 3. 작성

- `PLAN.md` 테스트 케이스 표의 TC마다 테스트 메서드를 하나 이상 만든다. 파일은 Edit·Write로만 쓴다(셸 쓰기 금지).
- 추적 표기: `@DisplayName("[TC-F01-03][REQ-012] 재고 부족 시 주문 거절")`처럼 TC와 REQ를 함께 적는다. `check-trace.sh`가 이 표기를 찾는다.
- 단언은 TC의 기대 결과를 구체 값으로 확인한다(상태 코드만이 아니라 응답 본문·에러 코드·저장된 데이터까지).
- 금지:
  - 테스트 대상 클래스 자체를 목으로 대체
  - 구현 로직을 테스트 안에 복제해 같은 계산 결과끼리 비교
  - 단언 없는 테스트, 예외를 삼키는 테스트
  - 실패하는 테스트를 통과시키려고 기대값을 구현에 맞춰 바꾸는 것
  - 테스트를 쓰는 중에 구현 코드(`src/main`·빌드 파일)를 같이 고치는 것. 결함을 발견하면 `HANDOFF.md` "구현 수정 요청"에 적고, 테스트 작성을 마친 뒤 `test-verify`의 실패 처리로 고친다.
- 외부 시스템(메시지 큐, 외부 API)은 `PLAN.md`가 정한 방식(Testcontainers, 목 서버 등)을 따른다. 정하지 않았거나 TC를 그대로 구현할 수 없으면(판정 불가 TC, 테스트 의존성 추가 필요) 멈추고 `feature-plan` 재계획으로 간다(`승인 취소` → `PLAN.md` "계획 변경 이력" → `계획 승인`).
- TC 묶음(테스트 파일 하나 또는 TC 3~5개)을 마칠 때마다 `HANDOFF.md` "진행 위치"를 갱신한다.

## 4. 마무리

- `artifacts/work/F-##/test-status.md`(없으면 `_template/`에서 복사)에 TC마다 행을 만들고 테스트 위치·관련 소스를 적는다. 새로 쓴 테스트의 상태는 `미실행`이다.
- `sh scripts/check-trace.sh feature F-##`가 `문제 없음`이어야 한다(명세 누락으로 보류한 TC는 그 사유와 함께 보고).
- `HANDOFF.md` 다음 행동을 `test-verify`로 갱신하고 같은 세션에서 이어 간다. 테스트 실행은 다음 단계에서 한다.
