# 하네스 업데이트

하네스 도입 예외(`workflow.md` "예외")와 같은 범위다. 하네스 파일(`.harness/paths`)만 바꾸고, 소스와 프로젝트 문서 내용은 바꾸지 않는다.

## 0. 업데이트 시점 판단

세션 시작 훅이나 `work-start`가 `sh .harness/hooks/harness-version.sh`로 구버전을 알리면 이 절부터 한다. 최신 여부는 `.harness/version`과 원본 `main` 커밋의 해시만 비교한 결과다. 다르면 업데이트 대상이고, 아래 확인과 업데이트에는 필요한 만큼 시간을 쓴다.

- 무엇이 바뀌는지 먼저 본다: 임시 클론(1단계)에서 `git log --oneline <설치>..HEAD`와 `git diff --stat <설치> HEAD`. 특히 아래를 사용자에게 알린다.
  - `docs/requirements.md`·`docs/prd/`·`docs/api/` 템플릿 변경 → 진행 중 feature의 PRD 승인에 영향(3단계)
  - `.claude/settings.json` 훅 등록 변경 → 업데이트 후 세션 재시작 필요
  - 규칙·스킬의 절차 변경 → 진행 중 티켓의 다음 단계부터 적용됨

| 상황 | 처리 |
| --- | --- |
| 통합 브랜치, 미커밋 변경 없음 (`work-start` 직전 포함) | 바로 1단계부터 진행. 보호 브랜치라 `하네스 업데이트 승인` 필요. 끝나면 하던 작업(`work-start` 등)으로 돌아감 |
| 작업 브랜치, 티켓 진행 중 | 기본은 미룸: 바뀌는 내용을 알리고, 지금 티켓을 마친 뒤 다음 `work-start`에서 업데이트. 사용자가 지금 하기를 원하면 미커밋 변경을 `itd-commit`으로 커밋하고 통합 브랜치로 전환해 업데이트한 뒤, 작업 브랜치로 돌아가 통합 브랜치를 병합(문서가 바뀌면 PRD 재승인 필요). 진행 위치는 `HANDOFF.md`에 먼저 적음 |
| 미커밋 변경 있음 | 업데이트하지 않음. 커밋(`itd-commit`)한 뒤 위 기준으로 다시 판단 |
| 확인 불가(네트워크) | 넘어가고 다음 세션에서 다시 확인 |

- 사용자가 미루기를 고르면 그대로 하던 작업을 계속한다. 세션마다 알림 한 줄이 다시 나오는 것은 정상이다.

## 0-1. 사전 확인

- `git status`가 깨끗해야 한다. 미커밋 변경이 있으면 멈춘다.
- 기준 버전(설치 당시 하네스 커밋)을 정한다.
  - `.harness/version`이 있으면 그 값
  - 없으면(초기 버전 설치 프로젝트) 사용자에게 묻는다. 모르면 `.harness/hooks/` 파일과 하네스 이력을 비교해 후보 커밋을 찾아 보여주고 확인받는다.
- Windows에서는 Git Bash에서 실행하고, `jq`·`node`가 설치되어 있는지 확인한다. `jq`가 없으면 `하네스 업데이트 승인`이 기록되지 않는다.
- 대상 브랜치를 확인한다. 보호 브랜치(main 등)에 바로 반영하거나 작업 브랜치(`feat/ITD-####`)에서 PR로 반영할 수 있다. 사용자에게 고르게 한다. 진행 중인 다른 작업 브랜치는 통합 브랜치를 병합해야 새 하네스를 받는다.

## 1. 병합 실행

```bash
tmp=$(mktemp -d)
git clone -q https://github.com/sju3358/harness-with-claude.git "$tmp/harness"
sh "$tmp/harness/.harness/update.sh" <기준 커밋|-> "$tmp/harness"
```

- 새 버전의 스크립트로 실행한다(프로젝트에 설치된 `update.sh`가 아니라 임시 클론의 것).
- 결과는 `.harness/update/report.txt`에 남는다. 종료 코드 1이면 충돌이 있다는 뜻이다.
- `$tmp`는 6단계까지 쓰고 지운다.

| 결과 | 뜻 |
| --- | --- |
| 추가·갱신·링크·삭제 | 프로젝트가 고치지 않은 파일이라 새 버전으로 그대로 반영 |
| 병합 | 양쪽이 고친 파일, 자동 병합 성공 |
| 충돌 | 양쪽이 같은 곳을 고침. 충돌 표시(`<<<<<<< 프로젝트`)가 파일에 남음 |
| 삭제보류 | 새 버전에서 없어졌지만 프로젝트가 고친 파일. 그대로 둠 |
| 줄바꿈 | 내용은 같고 CRLF로 체크아웃돼 있던 파일. LF로 다시 씀 (Windows) |
| 템플릿변경 | 프로젝트 문서(`.harness/seed`)의 템플릿이 바뀜. diff만 남음 |

- `충돌 … 상위 경로가 링크 또는 파일`이 나오면 그 경로가 `삭제보류`된 것이다. 사용자에게 보여주고 정리한 뒤 같은 기준 커밋으로 다시 실행한다.

## 2. 충돌 정리

- 충돌 파일마다 양쪽 내용을 보여주고 정한다. 프로젝트 전용 규칙(스택, 고객사 규칙)은 프로젝트 쪽, 하네스 절차·훅은 새 버전 쪽이 기본이다. 애매하면 사용자에게 묻는다.
- `grep -rln '^<<<<<<< 프로젝트' .`로 충돌 표시가 남지 않았는지 확인한다.
- `삭제보류` 파일은 목록으로 보고하고 사용자가 정한다.
- Claude·Codex 분업 버전에서 올라오는 경우 `AGENTS.md`, `.codex/`, `.agents/`, `.harness/hooks/codex-tool-adapter.mjs`가 삭제되거나 삭제보류된다. 삭제보류된 `AGENTS.md`·`.codex/`에 프로젝트 고유 규칙이 있으면 `CLAUDE.md` "프로젝트 규칙"으로 옮길지 사용자에게 묻고, 확인을 받은 뒤 지운다. 프로젝트 `.claude/settings.json`에 병합된 훅 명령의 `edit-guard.sh" claude` 인자는 무시되므로 그대로 둬도 된다.

## 3. 템플릿 변경 반영

- `.harness/update/seed/*.diff`를 읽고 프로젝트 문서에 구조 변경(새 절, 새 항목)만 옮긴다. 프로젝트가 채운 값은 건드리지 않는다.
- `docs/requirements.md`, `docs/prd/**`, `docs/api/**`를 바꾸면 PRD 승인 해시가 깨져 재승인이 필요하다. 진행 중 feature가 있으면 이 문서들의 템플릿 변경은 미뤄 두고 다음 `prd-change` 때 반영하도록 보고한다. `docs/project.md`, `docs/traceability.md`는 승인과 무관하므로 바로 반영해도 된다.
- 업데이트로 `docs/api/`에 새 파일이 추가된 경우도 해시가 바뀐다. `sh .harness/hooks/prd-check.sh` 결과를 보고한다.
- API 문서가 여러 파일(도메인별 파일, `CHANGELOG.md`)로 나뉜 이전 구조면 업데이트 뒤에도 그대로 동작한다(검사 스크립트가 `docs/api/*.md`를 모두 읽음). 다만 엔드포인트의 feature 연결은 이제 feature 명세 API 표에서만 읽으므로 `check-trace.sh prd`로 누락을 확인한다. 한 장(`README.md`)으로 합치는 일은 문서 변경이라 다음 티켓의 `api-design`(승인된 문서면 `prd-change`)에서 한다고 보고한다.

## 4. 검증

```bash
jq empty .claude/settings.json
for f in .harness/hooks/*.sh .githooks/* scripts/*.sh; do sh -n "$f" || echo "문법 오류: $f"; done
node --check scripts/check-api.mjs
git config core.hooksPath
```

- 실패하면 원인을 고친다. 고칠 수 없으면 커밋하지 않고 보고한다.
- 훅 등록(`.claude/settings.json`)이 바뀌었으면 세션을 다시 시작해야 반영된다고 알린다. 훅 스크립트 내용 변경은 바로 반영된다.

## 5. 커밋·push

- 하네스 파일만 stage한다. `.harness/paths` 목록 경로만 `git add`하고, `git diff --cached --name-only`로 확인한다.
- 커밋 메시지: `chore: 하네스 업데이트 (<기준 7자리> → <새 7자리>)`. 본문에 주요 변경과 충돌 정리 내용을 bullet로 쓴다.
- 보호 브랜치면 사용자에게 `하네스 업데이트 승인`을 한 줄로 입력하게 한다. 작업 브랜치면 일반 `커밋 승인`·`푸시 승인`이다.
- 커밋과 push는 따로 실행한다(staged 파일 검사).

## 6. 보고

- 기준 → 새 버전, 결과 건수, 충돌 정리 내용, 미뤄 둔 템플릿 변경, PRD 승인 상태, 세션 재시작 필요 여부, 커밋 해시.
- `rm -rf "$tmp"`로 임시 클론을 지운다.
