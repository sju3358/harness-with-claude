# API 문서 설계·수정

API 문서는 **`docs/api/README.md` 한 파일**이다. 프론트엔드 개발자에게 이 파일만 보내면 연동할 수 있어야 한다. API 문서는 PRD와 함께 승인 대상이다. 승인된 뒤 고치는 경우는 `prd-change` 흐름으로 진행하고, 그 안에서 이 스킬의 3·4단계를 따른다.

## 문서 원칙

- **한 장**: 도메인·기능별로 파일을 나누지 않는다. 별도 변경 이력 파일도 만들지 않는다. 엔드포인트가 많으면 "엔드포인트 목록" 표와 상세 절의 순서로 정리한다(도메인 묶음은 목록 표의 순서나 소제목 없이 설명 칸으로 구분).
- **자체 완결**: 다른 문서(PRD, `02-common.md`, feature 명세, 코드)를 가리키지 않는다. "자세한 건 ~ 참고", 문서 경로·`문서#섹션` 링크를 쓰지 않는다. 공통 규약·에러 코드·형식은 이 문서 안에 값으로 적는다.
- **FE에 필요한 것만**: 요청·응답 필드, 타입, 필수, null 가능, 제약, 에러와 프론트 처리, 인증, 형식, API 상태, 변경 이력과 프론트 영향. 아래는 쓰지 않는다.
  - REQ·feature·TC ID, PRD 버전, 근거 문서, 작성·검증 절차 같은 내부 추적 정보(연결은 feature 명세 API 표에 둔다)
  - 내부 구현(클래스·테이블·쿼리·메시지 큐·배치), 서버 내부 처리 순서. FE가 결과로 관찰하는 동작(예: "주문 후 재고가 즉시 차감되어 다시 조회하면 줄어든 값")만 적는다
- `API-###` ID와 제목 줄 `### API-### 메서드 경로` 형식은 유지한다(FE와 소통하는 이름이자 `check-api.mjs`·`check-trace.sh`가 읽는 줄).

## 0. 준비

- `docs/prd/00-overview.md`, `docs/prd/02-common.md`, `docs/prd/features/F-##.md`, 기존 `docs/api/`를 읽는다.
- 기존 프로젝트면 현재 컨트롤러 코드를 읽고 `node scripts/check-api.mjs` 출력으로 문서와 코드의 차이를 먼저 파악한다. 기존 API의 동작을 문서화할 때는 코드를 근거로 쓰고, 바꾸는 것은 PRD 근거가 있을 때만 바꾼다.
- `docs/api/`에 `README.md` 말고 다른 문서(이전 버전의 도메인별 파일, `CHANGELOG.md`)가 있으면 그 내용을 `README.md`로 옮기고 파일을 지우는 것까지 이번 작업에 포함한다고 사용자에게 알린다. 승인된 문서면 `prd-change`로 진행한다.
- 작업 브랜치가 `feat|fix/ITD-####`인지 확인한다. 아니면 `work-start`부터.

## 1. 공통 규약 (1절)

- `02-common.md`의 API 규약(응답 포맷, 에러 코드, 인증, 페이지네이션, 형식)을 프론트가 바로 쓸 수 있는 형태(예시 JSON, 프론트 처리)로 옮긴다. `02-common.md`에는 설계 근거를, 이 문서에는 사용법과 값을 쓴다. 두 문서의 값은 같아야 한다.
- 비어 있는 규약(날짜 형식, null 처리 등)이 있으면 사용자에게 묻는다. 정해지지 않은 채로 엔드포인트를 쓰지 않는다.

## 2. 엔드포인트 (2·3절)

- feature 명세 API 표의 엔드포인트마다 3절 형식으로 쓰고 2절 목록에 행을 추가한다. ID는 한번 정하면 바꾸거나 재사용하지 않는다.
- feature 명세 API 표(`| API-### | 메서드 | 경로 | 설명 | 요구사항 |`)가 API ↔ feature ↔ REQ 연결의 원본이다. 여러 feature가 함께 쓰는 엔드포인트는 각 feature 명세의 API 표에 모두 넣는다. API 문서에는 REQ·feature를 적지 않는다.
- 필드마다 타입, 필수, null 가능, 제약을 빠짐없이 쓴다. 프론트가 "이 필드가 없을 수도 있나?"를 물을 필요가 없어야 한다.
- 정상 응답 예시 JSON과, 해당 API에서 날 수 있는 에러(공통 에러 중 해당하는 것 + 고유 에러)와 프론트 처리를 쓴다. 공통 에러는 "1절 참고"가 아니라 코드를 그대로 다시 적는다(엔드포인트 절만 읽어도 처리할 수 있게).
- PRD에 없는 필드·엔드포인트를 임의로 추가하지 않는다. 필요하면 사용자에게 제안하고, 받아들여지면 PRD(feature 명세)에도 반영한다.
- feature 명세 API 표에는 ID·메서드·경로·설명·요구사항만 두고 필드 상세는 쓰지 않는다(두 곳에 상세를 쓰지 않음).

## 3. 수정일 때

- 바꾸는 엔드포인트의 `API 상태`를 `변경`으로, 없애는 것은 `폐기 예정` 또는 `폐기`로 바꾼다. 문서에서 지우지 않는다.
- 4절 "변경 이력"에 버전, 일자, API ID, 바꾸기 전 → 후, 프론트 영향(`없음`·`추가 대응`·`수정 필요`)을 적는다. 변경 근거(REQ, 요청 번호)는 이 문서가 아니라 PRD 변경 이력에 적는다.
- 문서 머리의 `- 버전:`을 올린다.

## 4. 마무리

- 자체 점검: 문서에 다른 파일 경로·`REQ-`·`F-`·`TC-`·`PRD` 같은 내부 표기가 남지 않았는지(`grep -nE 'REQ-|F-[0-9]|TC-F|docs/|\.md' docs/api/README.md`), `docs/api/`에 `README.md` 한 파일만 있는지 확인한다.
- `sh scripts/check-trace.sh prd`로 API ID ↔ feature 명세 연결 누락을 고친다.
- 기존 프로젝트면 `node scripts/check-api.mjs`를 다시 실행해 결과를 보고한다(새로 설계한 API는 아직 코드가 없으므로 `미구현`으로 나오는 게 정상).
- 프론트 전달용 요약을 만든다: 이번 버전의 API 수, 신규·변경·폐기 목록, `수정 필요` 항목. 사용자가 문서와 함께 붙여 보낼 수 있는 짧은 텍스트로 준다.
- 다음 단계: `prd-verify` (API 문서도 함께 검증·승인).
